## 4. P1 — Invite Experience Overhaul

### P1-1: Make AI-generated email draft EDITABLE before send

**Problem:** The AI draft preview (subject, emailBody, smsBody) renders in `readOnly` textareas. The user cannot edit the generated copy before it's applied. This defeats the purpose of AI-assisted drafting.

**Current code** ([EventsPage.tsx](../frontend/src/pages/EventsPage.tsx) lines 895–899):
```tsx

<textarea className="form-textarea" rows={6} readOnly value={aiDraftResult.emailBody} />
<textarea className="form-textarea" rows={3} readOnly value={aiDraftResult.smsBody} />
```

**Note:** The backend already supports user-edited overrides via `POST /admin/ai/invite-draft/apply` — the fields (subject, emailBody, smsBody) can all be overridden. The frontend just doesn't let users edit them.

**Action:**
1. Remove `readOnly` from all three textareas
2. Store the displayed values in component state (e.g., `editedSubject`, `editedEmailBody`, `editedSmsBody`) initialized from `aiDraftResult`
3. On "Apply Draft" action, send the **edited** values (not the original AI values)
4. Add a "Reset to AI Draft" button to revert edits
5. Visual indicator showing which fields have been manually edited

**Files:** `frontend/src/pages/EventsPage.tsx`  
**Risk:** Low — backend already accepts overrides

## 5. P2 — Naming Consistency (Mentor → Volunteer)

### P2-1: Delete "MENTORS" group and merge into "VOLUNTEERS" in production DB

**Problem:** The Target Groups checkboxes (user screenshot) show "MENTORS" even though the rest of the UI uses "Volunteers." The schema seeds both `MENTORS` (legacy) and `VOLUNTEERS` groups, but production still has members assigned to `MENTORS`.

**Decision (Q2 answer): Delete MENTORS.** Clean delete, no deprecation — but must be thoroughly verified.

**Current schema** (`database/schema.sql` lines 770–777):
```sql
-- Legacy: MENTORS still seeded for backward compatibility
IF NOT EXISTS (SELECT 1 FROM dbo.[group] WHERE group_name = 'MENTORS')
    INSERT INTO dbo.[group] (group_id, group_name, description, is_system)
    VALUES (NEWID(), 'MENTORS', 'Mentors / guides', 1);

-- New: VOLUNTEERS
IF NOT EXISTS (SELECT 1 FROM dbo.[group] WHERE group_name = 'VOLUNTEERS')
    INSERT INTO dbo.[group] (group_id, group_name, description, is_system)
    VALUES (NEWID(), 'VOLUNTEERS', 'Volunteers / guides', 1);
```

**Action:**
1. **Pre-flight audit:** Query all tables referencing MENTORS group_id:
   - `member_group` — count rows
   - `event_notification_target` — count rows
   - `notification_log` — count rows (audit only, no migration needed)
   - Any other FK references
2. **Migration script (idempotent, transactional):**
   ```sql
   BEGIN TRANSACTION;
   -- Move member_group assignments
   UPDATE mg SET mg.group_id = v.group_id
   FROM dbo.member_group mg
   INNER JOIN dbo.[group] m ON mg.group_id = m.group_id AND m.group_name = 'MENTORS'
   CROSS JOIN (SELECT group_id FROM dbo.[group] WHERE group_name = 'VOLUNTEERS') v
   WHERE NOT EXISTS (
     SELECT 1 FROM dbo.member_group existing
     WHERE existing.member_id = mg.member_id AND existing.group_id = v.group_id
   );
   -- Delete duplicate member_group rows (member already in VOLUNTEERS)
   DELETE mg FROM dbo.member_group mg
   INNER JOIN dbo.[group] m ON mg.group_id = m.group_id AND m.group_name = 'MENTORS';
   -- Move event_notification_target
   UPDATE ent SET ent.group_id = v.group_id
   FROM dbo.event_notification_target ent
   INNER JOIN dbo.[group] m ON ent.group_id = m.group_id AND m.group_name = 'MENTORS'
   CROSS JOIN (SELECT group_id FROM dbo.[group] WHERE group_name = 'VOLUNTEERS') v;
   -- Delete the MENTORS group
   DELETE FROM dbo.[group] WHERE group_name = 'MENTORS';
   COMMIT;
   ```
3. **Remove MENTORS seed** from `schema.sql` entirely
4. **Verify zero references remain:** `SELECT * FROM dbo.member_group mg JOIN dbo.[group] g ON mg.group_id = g.group_id WHERE g.group_name = 'MENTORS'` → 0 rows

**Files:** `database/schema.sql`, new migration script `scripts/migrate-mentors-to-volunteers.sql`  
**Risk:** Medium — must preserve member-group assignments, handle duplicates  
**Verification:** Query production for any remaining MENTORS references = 0. UI shows only VOLUNTEERS in Target Groups.

## 6. P3 — Duplicate Notification Protection

### P3-1: Add notification send cooldown per event + channel

**Problem:** User received two identical invite emails within 5 minutes. Root cause: **zero duplicate detection** exists. `sendEventPublishedNotification()` sends to all targets unconditionally every time it's called.

**Multiple trigger paths in `events.ts`:**
- `PUT /events/:id/status` → status becomes `published` → sends invites
- `PUT /events/:id` → `invitation_stage` changes on published event → sends invites
- `PUT /events/:id` → other fields change on published event → sends update notification

**Action:**
1. **Add dedup check** before `sendEventPublishedNotification()`:
   ```sql
   SELECT COUNT(*) FROM notification_log
   WHERE event_id = @eventId
     AND operation_type = 'event_published'
     AND status = 'sent'
     AND sent_at > DATEADD(MINUTE, -30, GETUTCDATE())
   ```
   If count > 0, skip the send and log a `skipped_cooldown` entry.
2. **Edits to a published event NEVER auto-send.** Notifications on edit are entirely user-initiated (see P3-2).
3. **Add `notification_log` unique index** for dedup safety:
   ```sql
   CREATE UNIQUE INDEX UX_notification_dedup
   ON notification_log(event_id, member_id, channel, operation_type, dedup_window_id)
   ```
   Where `dedup_window_id` is a computed column: `CONVERT(VARCHAR, sent_at, 112) + CAST(DATEPART(HOUR, sent_at) AS VARCHAR)`

**Files:** `backend/src/services/notifications.ts`, `backend/src/routes/events.ts`, `database/schema.sql`, `frontend/src/pages/EventsPage.tsx`  
**Risk:** Medium — must not block legitimate resends  
**Verification:** Publish event → edit immediately → confirm only one email received

### P3-2: Publish = Send; Edit ≠ Send; "Send Update" = explicit re-send

**Confirmed behavior (Q1 answer):**
- **Publish triggers send.** When the event creator clicks "Publish" (draft → published), that IS the send trigger. Ideally show a **final email preview popup** before committing so the creator can confirm the content.
- **Editing a published event NEVER auto-sends.** The creator may go back to fix a location description, check something, adjust wording — none of that should trigger a notification.
- **"Send Update" is a separate explicit action.** After editing a published event, the creator can choose to click a "Send Update" button to notify RSVP'd members about changes. This requires:
  - An Update Reason (sent to RSVP'd members so they know what changed)
  - Target group selection
  - Confirmation dialog

**Action:**
1. **Publish flow:** `PUT /events/:id/status` with `status: 'published'` → show email preview popup → on confirm, send invites. If preview is dismissed, still publish but skip send (or cancel publish — TBD).
2. **Edit flow:** `PUT /events/:id` on a published event → save silently, zero notifications.
3. **Send Update flow:** New explicit action `POST /events/:id/send-update` → requires `update_reason` + `notification_targets` in body → sends update notification to RSVP'd members in selected target groups.
4. **UI changes:**
   - Remove auto-send on edit from `events.ts` PUT route
   - Add "Send Update" button on published event card (only shows after edits have been saved)
   - Add notification send history panel: "Last sent: [date] to [N] members"
   - Add email preview modal before initial publish send

**Files:** `backend/src/routes/events.ts`, `frontend/src/pages/EventsPage.tsx`  
**Risk:** Medium — changes the core publish flow  
**Verification:** Publish event → preview shown → confirm → emails sent. Edit event → no emails. Click "Send Update" → update emails sent.

### P4-2: County-based location geocoding with program-level configuration

**Problem:** "The system should ALWAYS assume it to be in Colorado unless it's very explicitly described otherwise." The geocoding (Nominatim OSM) returns results globally. User wants county-level precision for common areas.

**Geocoding priority rules (confirmed):**
1. **User explicitly types a town or state** → use that first, override all rules below
2. **Address matches a configured primary county** → accept immediately
3. **Address is in Colorado but outside primary counties** → accept with info note
4. **Address is outside Colorado** → show warning: "This location appears to be outside Colorado. Is this correct?"

**Action:**
1. **Create a program-level geo config** (stored in DB or environment):
   ```json
   {
     "program": "Colorado Alpine",
     "state": "Colorado",
     "country": "USA",
     "primary_counties": ["Summit", "Eagle", "Routt", "Grand", "Park", "Garfield", "Lake"],
     "viewbox": "-109.06,36.99,-102.04,41.0"
   }
   ```
2. **Bias Nominatim queries** with the program's viewbox: `viewbox=...&bounded=0` (prefer but don't exclude)
3. **Append ", Colorado, USA" to geocoding queries** unless the input already contains a state/country qualifier
4. **County validation:** After geocoding, check if the result county is in `primary_counties`. Display:
   - ✅ "Summit County, CO" (primary county — green indicator)
   - ⚠️ "Denver County, CO" (Colorado but outside primary — amber note)
   - ❌ "Summit County, OH" (outside Colorado — red warning + confirmation)
5. **Show geocoding results** with full county + state so the user can verify
6. **Common locations dropdown** should also show the county for each saved location

**Files:** `frontend/src/pages/EventsPage.tsx` (location validation), new `backend/src/config/programGeoConfig.ts` or DB table  
**Risk:** Low-Medium — Nominatim reverse geocoding includes county in response; need to parse `address.county` field  
**Verification:** Type "Summit County Community Center" → geocodes to Summit County, Colorado (not Ohio). Type "Denver" → shows amber county warning but accepts.

## 10. Cross-Cutting Concerns

### Email client compatibility testing

Every change to `eventInvite.ts` (and other email templates) must be tested in:
- **Outlook Desktop** (Windows) — most restrictive HTML/CSS support
- **Outlook Web (OWA)** — slightly more permissive
- **Gmail (web)** — clips emails > 102KB, strips certain CSS
- **Apple Mail** — generally good HTML support
- **Gmail (mobile)** — responsive layout testing

**Recommendation:** Use [Litmus](https://litmus.com) or [Email on Acid](https://www.emailonacid.com) for automated rendering previews, or manually test with the five clients above.

### Database migration safety

All schema changes (P0-1, P2-1, P3-1) should:
1. Be scripted in an idempotent migration file (IF NOT EXISTS guards)
2. Be tested against a staging DB first
3. Have a rollback script
4. Be run during a maintenance window with no active blast sends

### AI prompt iteration

P1-4 (improve AI quality) is inherently iterative. Plan for:
1. First pass: Enrich system prompt with event context
2. Test with 5+ diverse events
3. Collect feedback
4. Second pass: Adjust based on results
5. Consider A/B comparison: show old vs new prompt output side-by-side
